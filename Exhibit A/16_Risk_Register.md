# 16 — Risk Register

Likelihood and Impact are rated Low / Medium / High. This register covers technical risk only — it does not restate the safety/security controls already specified as *requirements* in `01_Requirements.md` and `14_Security.md`; it covers what could still go wrong *around* those controls.

| ID | Risk | Likelihood | Impact | Mitigation | Notes |
|---|---|---|---|---|---|
| R-01 | A gap in `validate_action`'s bound logic lets an unsafe action through | Low (given property-based fuzz testing, §8 of `13_Testing.md`) | High | Exhaustive property-based testing of the validator specifically; independent re-validation inside `apply_setpoints` itself as a second, redundant check (`09_MCP_Architecture.md` §2.7) | This is the single highest-impact risk in the system and the reason two independent checks exist for the same property, not one |
| R-02 | EnergyPlus fatal error mid-run | Medium | Medium | Graceful termination with partial-result flushing (`05_Runtime_Execution.md` §6); `RunSummary.status = incomplete` rather than silently marked complete | Fatal errors are a normal occurrence in EnergyPlus development generally, not unique to this project |
| R-03 | Local LLM inference server crashes or runs out of memory mid-run | Medium | Medium | Degraded-mode fallback controller (RR-3, `01_Requirements.md`); health-check-driven reconnection attempts; run continues rather than aborting | Directly tested via fault injection (`13_Testing.md` §5) |
| R-04 | A full-annual, every-timestep AI-driven run is impractically slow given LLM latency | High if attempted as literally described | Medium (schedule risk to the PoC timeline, not a correctness risk) | Representative-day sampling strategy adopted explicitly as a requirement, not discovered as a limitation late (`01_Requirements.md` PR-3) | This is the risk this Project Bible is most deliberately pre-empting rather than discovering during implementation |
| R-05 | Agent context grows unboundedly over a multi-day run, causing latency blowup or a context-length error | Medium absent mitigation | Medium | Two-tier memory (rolling window + periodic reflection) and "pull not push" history access (`08_LLM_and_Agent_System.md` §3, `15_Performance.md` §3) | Covered by dedicated stress tests (`13_Testing.md` §6) |
| R-06 | Overly aggressive energy optimization sacrifices comfort | Medium absent explicit constraint structure | High (directly undermines the rubric's Thermal Comfort criterion) | Hard PMV band as a genuine constraint, not just a penalty term (`06_Control_System.md` §3); acceptance criterion S5 requires agent-run comfort compliance ≥ baseline's own compliance, not just "acceptable in isolation" | This risk is exactly why S5 exists as a named acceptance criterion rather than trusting S3/S4 alone |
| R-07 | LLM sampling non-determinism makes the demo run hard to reproduce on request | Medium | Low–Medium | Deterministic-sampling configuration available and used for the regression suite and the recorded demo (`13_Testing.md` §9); full decision trace logged regardless, so even a non-reproduced run's specific behavior remains fully inspectable after the fact | Non-determinism itself is not treated as a defect (§9, `13_Testing.md`) |
| R-08 | EnergyPlus Python API surface changes in a future version, breaking actuator/handle resolution | Low within the PoC's timeline, higher over a longer maintenance horizon | Medium | Explicit version pinning and startup-time validation of every actuator/variable name against the actually-loaded `.idf` (`07_EnergyPlus_Design.md` §8) rather than assuming names carry over unchanged | The API is documented by its maintainers as evolving additively, which lowers but doesn't eliminate this risk |
| R-09 | Demo-day environment lacks a GPU capable of running the target model at budget latency | Medium | High for the specific demo event, low for the project's technical validity otherwise | Documented smaller/quantized CPU-runnable fallback model as a named contingency, plus a pre-recorded run as a last-resort backup for the demo video specifically | This is an operational/logistics risk, not a design flaw, but it's real enough to name explicitly |
| R-10 | A live external data feed (if the weather/utility stub is ever swapped for a real one) introduces untrusted content into the agent's context | Low for the PoC (stubs are local files), Medium if/when swapped for a live feed | Medium | Treat all such content as untrusted per `14_Security.md` §2; the validator gate does not depend on the content of any upstream feed being trustworthy | Named now, before the swap happens, specifically so it isn't an afterthought when it does |
| R-11 | Config-actuator/`.idf` mismatch discovered only mid-run instead of at startup | Low (explicit startup validation is a stated requirement) | Medium | Startup-time schema and handle-resolution validation (`01_Requirements.md` §12 edge case; `12_API_Design.md` §3) | Cheap to prevent, expensive to debug if it slips through — worth the startup-time cost |
| R-12 | Async logging buffer backpressure silently drops more than intended under sustained Storage slowness | Low | Low–Medium (audit-trail completeness, not simulation correctness) | Documented, deliberate drop-priority order (lowest-value telemetry first, never `DecisionLog`/`Incident`, `04_Dataflow.md` §3); Monitoring surfaces buffer-pressure as its own signal | A availability/completeness risk to the record, not to the running simulation |
