# 08 — LLM and Agent System

## 1. The candidates, and what each actually buys

| Architecture | What it adds over a plain prompt-response call | Cost |
|---|---|---|
| Single agent, direct tool use | The model can act on the world, not just describe it | Minimal — one model, one loop |
| **ReAct** (interleaved reasoning + acting) | Explicit "thought" steps interleaved with tool calls, so the model's intermediate reasoning is visible and can inform the *next* action, not just the final answer | One model, but more tokens/turns per decision than a single-shot call |
| Multi-agent (separate Planner / Executor / Critic models or roles) | Specialization — a planner model doesn't also have to be good at low-level execution or self-critique | Multiplies LLM calls (and therefore latency and inference cost) per decision, roughly proportional to the number of roles |
| **Reflexion** (self-critique + episodic memory) | Learning from *past* failures without any weight updates — a failed attempt is converted into a natural-language lesson stored in memory and surfaced on future attempts | An extra evaluation + reflection step, but only needed after a failure or at a natural checkpoint, not every cycle |
| Tree search / deliberate search (Tree-of-Thought, LATS-style) | Explores multiple candidate reasoning paths and backtracks, useful when the search space of *plans* is large and evaluable | Multiplies LLM calls by the branching factor × depth explored — often 5–20× a single ReAct pass |
| Long-context-only (no retrieval, stuff everything into the prompt) | Simplicity — no memory-management code | Cost grows with run length; and longer contexts don't just cost more, they also make models less reliable at using information buried in the middle of a long context, a well-documented "lost in the middle" effect |
| Reasoning-tuned / extended-thinking models | Better performance on genuinely hard multi-step problems that benefit from more deliberation before answering | Materially higher latency and token cost per call — works against a tight decision-cycle latency budget |

## 2. What this system's actual decision problem looks like

Before picking an architecture, it's worth being honest about what's being decided each cycle: a **small, bounded action** (a handful of setpoints, each already constrained to an allow-listed range) informed by a **modest amount of context** (current state, a forecast window, maybe recent history). This is not an open-ended planning problem with a huge branching factor, and it is not a problem where the *hard* part is numeric optimization (that's delegated to `propose_setpoints`, per `06_Control_System.md`). The hard part is *judgment under changing context* — how much to weight comfort vs. energy given today's forecast and the last few days' outcomes.

That framing directly shapes which architectures are worth their cost here.

## 3. Recommendation: ReAct as the per-cycle loop, Reflexion-style reflection as the cross-cycle loop, no multi-agent swarm, no tree search

**Per-cycle (the loop described in `05_Runtime_Execution.md` §4) is a single-agent ReAct loop**: the model alternates reasoning and tool calls (forecast → propose → validate → possibly revise → commit), with a bounded tool-call budget. This is chosen over multi-agent and tree-search designs for a direct reason: this project's LLM is a self-hosted open-weight model, not a frontier hosted one, and every additional LLM call in a multi-agent or tree-search design multiplies both the latency budget (already tight — `15_Performance.md`) and the chance of an individual call misbehaving. Given the action space per cycle is small and mostly delegated to a deterministic tool anyway, the marginal value of exploring multiple reasoning branches or splitting the reasoning across several models is low relative to what it costs in latency and reliability surface area — there just isn't enough decision complexity *left* in the LLM's job, after the numeric optimization is delegated away, to justify paying for a search or a multi-model pipeline.

**Cross-cycle, a lightweight Reflexion-style mechanism runs once per simulated day** (not every cycle): at the end-of-day boundary, the agent is shown a compact summary of the day's outcomes (energy used, comfort-band compliance, any incidents) and asked to produce a short natural-language reflection — what worked, what didn't, what to try differently — which is stored and included in future cycles' context (via Memory's reflection summary, `03_Component_Design.md` §5) instead of raw transcript. This is the system's actual "self-correction mechanism" (a rubric-scored criterion) and it is cheap: one extra LLM call per simulated day, not per cycle, because daily is the natural grain at which "did yesterday's strategy work" is even a meaningful question — evaluating it every 15 minutes would be noise, not signal.

This combination — inexpensive per-decision loop, occasional deeper reflection — mirrors how Reflexion itself is structured in the literature: an Actor (the ReAct-style policy), an Evaluator (here, the deterministic comfort/energy metrics computed by Analytics, not another LLM call, which is both cheaper and more objective than an LLM self-grading its own work), and a Self-Reflection step that only fires when there's something worth learning from, converting a coarse success/failure signal into a compact verbal lesson added to memory rather than requiring any gradient-based learning.

### Why the rejected options are actually rejected, not just "not chosen"

- **Multi-agent Planner/Executor/Critic**: rejected for this system specifically because the "planning" (what setpoint) is already deterministic and delegated, and the "criticism" (is this action safe) is already deterministic and delegated (`validate_action`). Splitting the *remaining* judgment-only task across multiple LLM calls would be adding agent-architecture complexity to compensate for a decision problem that this system's own control-strategy design (`06_Control_System.md`) has already simplified. If the deterministic optimizer/validator split did not exist — i.e., if this were a pure end-to-end LLM control system — a multi-agent Planner/Critic split would be far more defensible; it would just also be solving a problem this project has chosen not to have.
- **Tree search**: rejected because it pays for exploring alternative reasoning paths in a domain where the actual numeric alternatives are already enumerable and cheap to evaluate by the deterministic optimizer (which can just evaluate multiple candidate weightings directly, far more cheaply than exploring them via separate LLM-generated branches).
- **Long-context-only memory**: rejected in favor of the two-tier (rolling window + periodic reflection + on-demand `get_history` tool) design in `03_Component_Design.md` §5, precisely to avoid both the cost growth and the "lost in the middle" reliability problem of an ever-growing prompt over a multi-day run. This is also the direct answer to the brief's explicit deliverable requirement for "a technical approach for handling lengthy simulation logs" — the answer is: raw logs never enter the LLM's context by default at all; only compact summaries and on-demand, filtered query results do (elaborated further in `15_Performance.md` §2).
- **Reasoning-tuned/extended-thinking models for the per-cycle loop**: rejected for the tight loop given the latency budget (`01_Requirements.md`, LR-1), but explicitly *permitted* for the once-a-day reflection step, where the latency budget is far looser and the task (synthesizing a day's worth of outcomes into a lesson) benefits more from deliberation than the fast per-cycle loop does.

## 4. Related work — this is not being designed in a vacuum

A specific and growing body of 2024–2026 research addresses LLMs in building energy control directly, and this design is positioned against it rather than ignoring it:

- A recent survey (Liu, Zhang, Chen, Chen, Yang, Lo, Wen, and O'Neill, *Building Simulation*, 2025) maps out where LLMs are being applied across the building-energy lifecycle — including using models as translators that can read and write EnergyPlus-style building-model objects with correct schema and cross-references, which is a *different* problem (automated model authoring) from this project's *runtime control* problem, and is a useful pointer for a future extension (an LLM that helps *build* the `.idf` variants for FR-11's ECM sweep) rather than something this PoC needs to solve.
- Sawada and colleagues' "Office-in-the-Loop" line of work investigates agentic AI directly for HVAC control decisions in an office setting, which is the closest published analogue to this project's control loop, and supports the general premise that agentic, tool-using LLMs are a viable — if still actively-researched — approach to this class of problem, not a purely speculative one.
- Retrieval-oriented approaches such as DARLIN (domain-guided retrieval for interpretable HVAC control) reinforce this project's own choice to keep historical grounding as an on-demand, retrieval-style tool call rather than an ever-growing prompt.
- Separately, EPlus-LLM (Jiang et al., *Applied Energy*, 2024) and related agentic-workflow papers on automated EnergyPlus model debugging address the brief's "extract runtime errors... execute tasks autonomously" language from the *model-authoring* side rather than the *runtime-control* side this project focuses on — a reasonable adjacent direction, and one this project's MCP tool surface (`09_MCP_Architecture.md`) could plausibly be extended toward later (e.g., an `explain_energyplus_error` tool), but is not built here.

## 5. Model and serving-stack requirements this architecture implies

- **Native or reliably constrained tool-calling.** As of this writing, mainstream local-serving stacks (Ollama, vLLM, llama.cpp-based servers) support native tool-calling schemas for current open-weight model families, and separately support decoder-level structured-output constraints (JSON-schema or grammar-constrained decoding) as a hard guarantee of syntactic validity, independent of whether the model "wants" to comply. This project requires the constrained-decoding path to be enabled specifically for `propose_setpoints`/`apply_setpoints`-shaped calls, where a malformed call is not just an inconvenience but a system-reliability requirement (RR-1, `01_Requirements.md`). As covered in `06_Control_System.md` §1.5, this guarantees syntax, not correctness — the validator remains mandatory regardless.
- **A small, sharply defined tool surface.** Current practitioner guidance on local tool-calling models is consistent on this point: models — especially smaller, self-hosted ones — pick the *right* tool out of a large catalog less reliably than they format an individual call, so keeping the active tool count low (this project's roughly ten tools, `09_MCP_Architecture.md`) with sharp, unambiguous descriptions is a real reliability lever, not just a tidiness preference.
- **A specific model is not hard-coded into this design on purpose.** The open-weight model landscape has moved quickly even within the last year and will keep moving; this document specifies the *requirements* a chosen model/serving pair must meet (native or grammar-constrained tool calling; enough context for the rolling window plus tool schemas; acceptable latency on the available hardware per `15_Performance.md`) rather than betting the architecture on one named model. At time of writing, multiple current open-weight families (in the Llama, Qwen, and Mistral lineages, among others) meet these requirements at the 7–35B scale suitable for single-GPU self-hosting; the concrete choice should be revisited at implementation time against whatever hardware is actually available, using the requirements above as the selection test, not a fixed name.
